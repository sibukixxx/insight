# Insight Lab プロダクトブループリント

このドキュメントはエンジニアリング詳細ではなく、**「なぜこれを作っているか」「誰のためか」「今どこまで来ているか」** を、初めてこのプロジェクトを引き継ぐ人が最初に読む前提でまとめたものです。実装の詳細は [architecture.md](./architecture.md)、動かし方は [operations.md](./operations.md) を参照してください。

---

## 1. 一言で言うと

顧客インタビュー・レビュー・案件募集文・SNS投稿などのテキストから、本人も言語化できていない「隠れたニーズ」を、**AIの推測を鵜呑みにせず、原文照合済みの引用で裏付けながら**見つけるローカル実行型ツール。Go単一バイナリで配布し、ブラウザで完結する。

## 2. 誰のためのプロダクトか

このプロダクトには最初から two-track（二つの用途）がある。両方とも同じエンジン・同じコードベースで動く。

### 用途A: 営業・商談デモ（元々の出発点）
商談の場でその場で `./insight-lab --demo` を起動し、「AI APIを呼べるだけでなく、品質管理されたAI分析システムを設計・実装できる」ことを数分で証明する。ポートフォリオ／営業ツールとしての用途。

### 用途B: 自分自身の収益機会発見（開発途中で追加された用途）
「インサイトは本来マーケターが多数の顧客の声を突き合わせて『ここが違う』と気づく作業であり、それを他社に売り込むより自分で機会を見つけて自分で商品化した方が早いのでは」という指摘を受けて追加された用途。案件サイトの募集文やSNS投稿を貼り付けて解析すると、`Product Opportunity`（対象企業への改善提案）と並んで **`Monetization Angle`**（自分がこのニーズをどう商品化できるか）が出力される。

どちらの用途で使うかは、投入するデータソース（`SourceType`: interview/review/support/sales/survey/job_posting/social_post）と読み手が変わるだけで、パイプライン自体はドメイン非依存。

## 3. 価値提案・差別化

競合する「AIでインサイト分析」系ツールとの違いは機能の数ではなく、**信頼性の作り方**にある。

| 一般的なAI分析ツール | Insight Lab |
|---|---|
| AIが最終結論だけを出す | Insight → Evidence → 反証 → Confidence を必ずセットで出す |
| AIの引用をそのまま信じる | すべての引用をアプリ側で原文照合（grounding）。照合できない引用は破棄し、表示しない |
| Confidenceも含めAIの自己申告を信じる | Confidenceはアプリ側で機械的に計算（Evidence強度・カバレッジ・多様性・反証件数から算出）。LLMに数値を出させない |
| 「なぜその結論か」がブラックボックス | Observation → Pattern（繰り返しへの気づき）→ Rationale（推論の飛躍）→ Hypothesis → Evidence → Insight という連鎖をすべて保存し、UIでたどれる |
| デモ用データと納品物が曖昧に混在 | デモ用ビルドと納品用ビルドをGo build tagでコンパイル時に分離。納品用バイナリにはデモデータが一切リンクされないことをCIで検証 |

この「AIの出力を構造的に検証してから見せる」という設計思想が、単なるプロンプトエンジニアリングとの違い。

## 4. プロダクトの核となる原則（絶対に譲らない一線）

1. **Evidence（Insightを支持する引用）は必ず原文照合済みでなければならない。** LLMが生成した引用をそのまま画面に出すことは絶対にしない。
2. **Confidence・relevanceScoreはLLMに自己申告させない。** アプリ側で機械的に計算する。
3. **反証は必ず探す。** 支持する声だけを集めて終わりにしない。
4. **推論の中間過程（Pattern・Rationale）を捨てない。** 最終的な洞察の文章だけでなく、そこに至った経緯もすべて保存し、UIで確認できるようにする。
5. **デモ用データは納品用ビルドに一切混入させない。** コンパイル時に構造的に分離する（ランタイムのフラグ制御だけに頼らない）。
6. **APIキーはディスク・DBに保存しない。** プロセスメモリ上にのみ保持する。

これらはコードレビューやリファクタリングで崩れやすい部分なので、変更を加える際は必ず維持されているか確認すること。

## 5. 現在地（何が動くか）

Phase 1〜3が完了しており、**実際に動く状態**にある（フェイクLLMサーバー + 実HTTP + Playwrightでのブラウザ操作まで含めて検証済み）。

- 単一バイナリ起動、埋め込みUI、SQLite永続化
- デモ/納品ビルドの分離（`make build-demo` / `make build-delivery`）
- OpenAI互換LLM接続（3段フォールバック、リトライ、タイムアウト）
- Observation抽出 → Grounding Check → Pattern検出 → Hypothesis生成 → Evidence検索（支持+反証）→ Insight文章化 → 重複統合 → Confidence計算、という8段パイプライン
- Pattern・Rationaleの永続化と、Insight詳細画面での「推論の過程」表示
- SSEによる解析進捗のリアルタイム表示
- 評価指標5種（Evidence Coverage、Unsupported Claim Rate等）の計算・表示
- CSVインポート、設定画面（接続テスト付き）
- CI（gofmt/vet/test、納品ビルドへのデモデータ非混入の自動検証）

**未着手・未検証（Phase 4後半〜Phase 6）:**
- Golden Datasetによる回帰評価（実LLM前提のため）
- Markdownレポートエクスポート
- Contradiction Finder等の追加分析モジュール
- OS Keychain連携、`--local-only`モード
- 大規模プロジェクト（Observation数百件以上）でのスケール — 現状Evidence RetrievalはプロジェクトのObservation全件を毎回LLMに渡す設計で、トークン予算を圧迫しうる
- 実際のOpenAI APIキーでのエンドツーエンド検証（フェイクサーバーでの検証のみ。構造は本物のOpenAI Chat Completions APIに準拠しているが、実キーでの動作確認はまだ行っていない）

詳細なフェーズ別チェックリストは [implementation-plan.md](./implementation-plan.md) を参照。

## 6. まだ検証されていないこと・仮定にとどまっていること

引き継ぐ人が誤って「証明済み」と思い込まないよう、明示的に書いておく。

- **実際の商談・実務での利用実績はゼロ。** 設計は理にかなっているはずだが、実際に顧客に見せて刺さるかどうかは未検証。
- **Confidenceスコアの重み（Evidence強度35%・カバレッジ25%・多様性20%・パターン頻度20%）は初期値であり、実データでのチューニングは未実施。** Golden Datasetでの回帰評価を通じて調整する想定だが、そのGolden Dataset自体が未作成。
- **Monetization Angle機能は追加されたばかりで、実際に「自分で商品化する」フローの有効性は未検証。**
- **大規模データでのgrounding照合の精度・速度は未検証。** デモデータ（20件、各数百字程度）でしか動かしていない。

## 7. ロードマップ（優先順位の考え方）

次に着手するなら、以下の順序を推奨する（理由も添える）。

1. **実際のLLM APIキーでの動作確認** — フェイクサーバーでの検証だけでは、実際のOpenAI/Azure/Ollama等との差異（レスポンス形式の細かな違い、レートリミット挙動）を見逃す。最優先。
2. **Golden Dataset作成 + 回帰評価** — Confidence重みや プロンプトを調整する土台がないと、以降の改善が「勘」になる。
3. **実際に1〜2回、商談や自分の市場調査で使ってみる** — 用途A・用途Bそれぞれについて、机上の設計が実際に機能するかを検証する。ここで得たフィードバックが、次の機能追加の優先順位を決めるべき。
4. その上で、Phase 6（Contradiction Finder等の追加モジュール、スケール対応）に進む。

機能を先に増やすより、今あるものが実際のデータ・実際の場面で機能するかを確認する方が優先度が高い、というのがこのブループリントの立場。
